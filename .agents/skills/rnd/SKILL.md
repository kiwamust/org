# R&D局 — 知を掘り、知を編む

ファクトベースの知見を組織に供給する。仮説生成と検証のサイクルを回す。推測と事実の境界を明示する。

## GBT ポジション

**Generation** が主軸。価値探索・仮説生成・調査。Behavior へ渡す前の知的原材料を生産する。

## Obsidian Vault 連携

- パス: `~/Desktop/work/work`
- Vault 操作の詳細は以下のスキルに準拠:
  - `obsidian-search` — 検索手法（全文/構造化/意味検索）
  - `obsidian-link` — Wikilink 運用、関連ノート提案、MOC 分類
  - `obsidian-daily` — デイリーノート連携、タグ運用
- 成果物の出力先: `~/Desktop/work/work/org/research/{テーマ}/`

## エージェント構成

| Role                | 責務                                         |
| ------------------- | -------------------------------------------- |
| research-director   | 局全体の統括、調査設計、dispatch との連携    |
| analyst             | データ分析・統計処理・トレンド分析           |
| knowledge-architect | 知識体系の設計・MOC構築・概念マッピング      |
| fact-checker        | 主張・データの事実検証・出典の信頼性評価     |

## Workflow A: Research Project（調査プロジェクト）

### Step 1: 調査設計

research-director が調査チャーターを策定:

| 項目      | 内容                                     |
| --------- | ---------------------------------------- |
| リサーチQ | 何を明らかにするか（問いの定義）         |
| 仮説      | 現時点の仮説（あれば）                   |
| スコープ  | 調査対象の範囲・除外事項                 |
| 手法      | 文献調査 / データ分析 / Vault 横断検索等 |
| 材料      | 入力となる Vault ノート、URL、データ     |
| DoD       | 何をもって調査完了とするか               |

### Step 1.5: 基盤定義（形式モデリングを含むPJの場合）

形式的な数理モデルを扱うPJでは、情報収集（Step 2）の前に以下を確定させる:

| 項目       | 内容                                                   |
| ---------- | ------------------------------------------------------ |
| 状態空間 Ω | 何を「状態」と呼ぶか。粗視化の粒度と正当化             |
| 観測写像   | 観測イベント（コミット、PR、会議等）→ 状態への対応規則 |
| 時間粒度   | 離散化の時間窓。連続近似と離散モデルの整合性           |

基盤定義は後続の全タスクの前提（契約）。ここが揺れると全体が崩壊する。ただし基盤定義の成果物は「契約」に限定する。後段の結果に依存する成果物（最小データ要件、識別不能条件、推定手順等）は発生源タスクが書き、統合タスクが束ねる。

**Re-freeze Protocol（契約の改訂手順）:**

契約は凍結が前提だが、中間統合以降で契約自体に問題が発見される場合がある。その場合:

1. 発見者が research-director に報告（「T0 のどの定義が、なぜ不整合か」を明示）
2. research-director が影響範囲を評価（invalidate されるタスク成果物の一覧）
3. dispatch にエスカレーション（スコープ変更に該当）
4. ユーザー承認後、契約を改訂しバージョン番号を付与（T0v2）
5. invalidate されたタスクを再実行（再実行範囲はユーザーが承認）

Re-freeze は例外処理。頻発するなら粗視化粒度の選択自体を見直す。

**Tier 運用規則（形式モデリングPJ）:**

- **Tier 1（既存定理由来）**: 引用元定理を明記。適用条件の充足を検証。プロジェクト系への写像の正当性を論証
- **Tier 2（独自仮説）**: 仮説として明記。反証条件を定義。検証方法を提示

Tier タグは主張単位で付与する（Claim Tier Table）。1つの節に Tier 1 と Tier 2 が混在してよいが、混同は R02 不良。

**Claim Tier Table の必須列:**

- Claim: 主張の内容
- Tier: 1 or 2
- 根拠: 引用定理 or 翻訳仮説の根拠
- 条件仕様: Tier 1 → 適用条件の充足検証、Tier 2 → 棄却仕様（観測量・検定の型と方向・棄却域の方向・「Path C で確定」スタブ）

### Step 1.7: 中間統合点の設計

並列実行するタスク群がある場合、最終統合の前に中間統合チェックポイントを設計する:

- 並列タスクが同一の粗視化（状態空間・時間粒度）を前提としているか
- 操作的定義が相互に整合しているか
- Tier 分類が各タスク間で一貫しているか

中間統合は PQG として Operations 局の QAD本部に検査依頼する。識別可能性の一次判定（この観測設計で Tier 2 仮説が原理的に棄却可能か）を含める。

### Step 2: 情報収集

research-director がタスクを分解し、エージェントに割り当て:

- analyst → データ収集・定量分析
- knowledge-architect → Vault 内の既存知識の構造化
- fact-checker → 外部情報源の信頼性検証

各エージェントは Issue に進捗を記録する。

### Step 3: 統合・執筆

- synthesis-writer が収集結果を統合レポートに編む
- 出典と Wikilink を必ず含める
- 推測と事実を明確に区別する

### Step 4: 品質ゲート → 納品

Operations 局の UQG を通し、dispatch に完了報告。

## Workflow B: Knowledge Synthesis（知識統合）

Vault 内の既存知識を横断的に統合し、新しい構造を与える。

1. knowledge-architect がテーマに関連する Vault ノートを `obsidian-search` で探索
2. analyst が定量的パターン（頻出タグ、リンク密度、時系列変化）を分析
3. knowledge-architect が概念マップまたは MOC 草案を設計
4. synthesis-writer が統合ノートを執筆
5. vault-curator が成果物を Vault に配置し、既存ノートとリンク接続

成果物: `~/Desktop/work/work/org/research/{テーマ}/synthesis.md`

## Workflow C: Fact Verification（事実検証）

特定の主張・データの真偽を検証する。

1. fact-checker が検証対象の主張を構造化（主張・根拠・出典）
2. 一次情報源への追跡（出典の出典まで遡る）
3. 信頼性評価:

| レベル | 基準                       |
| ------ | -------------------------- |
| A      | 一次情報源で確認済み       |
| B      | 複数の信頼できる二次情報源 |
| C      | 単一の二次情報源           |
| D      | 出典不明・検証不能         |

4. 検証結果を Issue に記録し、research-director に報告

## 不良コード体系（R01-R10）

| コード | 不良内容                               |
| ------ | -------------------------------------- |
| R01    | 出典なし・出典不明                     |
| R02    | 推測と事実の未区別                     |
| R03    | リサーチ Q に対して回答不十分          |
| R04    | サンプルサイズ・範囲の不足             |
| R05    | 一次情報源未確認                       |
| R06    | Vault 既存知識との矛盾未解決           |
| R07    | 結論の飛躍（根拠から論理的に導けない） |
| R08    | バイアスの未考慮                       |
| R09    | 概念定義の曖昧さ                       |
| R10    | Wikilink/タグ規約違反                  |

## 制約

- ファクトベース。推測は「仮説:」と明記する
- 出典必須。出典のない主張は成果物に含めない
- 推測と事実を必ず区別する。混同は R02 不良
- Vault の Wikilink/タグ規約を遵守（`obsidian-link`/`obsidian-daily` 準拠）
- 成果物には元ノートへの Wikilink を必ず含める
- `Kiwamust_mobile_clone/` は検索対象から除外
- 他局の Issue を直接変更しない。dispatch 経由で連携
